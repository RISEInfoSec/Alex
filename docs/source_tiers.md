# Publication source tiers

`config/source_tiers.json` defines the publication-source designations and review priorities. A tier is routing evidence, not a numerical quality-score adjustment or a publication approval. Official HTTPS publication URLs establish a provisional source match; actual content and provenance still need review. Discovery-provider labels alone do not establish a publication's tier. SOUPS uses the broader-scope tier and is not included in the trusted-curated exception.

To add or change a source, update its tier, name and official host patterns in the registry, add positive and lookalike-host tests in `tests/test_source_tiers.py`, and review overlap with SOUPS and other sources. Site staging uses a copy at `data/source-tiers.json`; update it to exactly the same bytes and rerun the site source-tier and lifecycle tests before deployment. Source matching in both implementations must remain equivalent. Changes to a published site require the normal backup, migration and coordinated processing-engine transition; source changes do not authorize publication or edits to existing decisions.

Trusted-source core-term or relevance-floor failures route to human review and keep the original score and reasons. In the main pipeline, post-harvest failures are accumulated in `data/source_relevance_review.csv` using evidence-bound review identities. Each identity covers stable candidate and scoring fields, the tier, reasons, threshold and a recorded SHA-256 of the scoring and source-tier policies; a new evidence or policy version creates a distinct item. The existing state workflow preserves this queue on the `pipeline-state` branch like other intermediate CSVs; that branch's repository permissions apply to its contents. This generated queue is not a decision ledger or a publication authorization. A historic queue item may remain after a later editorial exclusion: any downstream consumer must recheck the current exclusion registry and other holds before acting. In private staging, relevance decisions are separately recorded against the reviewed evidence; a relevance approval does not resolve other holds and a separate editorial approval remains necessary. Existing human exclusions and unrelated decisions must not be silently reopened or overwritten.

For a separately obtained owner-authenticated staging export, `python -m scripts.reconcile_source_relevance` compares one exported `source_relevance_reviews` row and its optional `source_relevance_decisions` row with an exact main-queue item. It accepts a verified chunked staging SQL snapshot or a JSON packet with `reviews` and `decisions` arrays containing those table rows. Supply the export's independently recorded SHA-256, both exact review IDs, the staging policy and source-tier registry, and the exact hosted implementation hash that produced the staging checks; use `--help` for required arguments. The command reads local files and writes a result only to stdout. It fails closed on mismatched candidate content, score, checks, policy, source, exclusion or decision binding. A checksum confirms bytes, not the identity of the exporter: independently verify that the packet came from the owner-authenticated staging site. A missing decision remains pending. Even when relevance was approved, the result is **only a draft**, with editorial, classification and publication approvals all false; it contains no release target or passing-gate assertions. Reconcile independent holds and obtain a separate content-bound editorial/publication approval before using the existing controlled release process.
